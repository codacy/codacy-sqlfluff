# Codacy SQLFluff

This is the docker engine we use at Codacy to have [SQLFluff](https://docs.sqlfluff.com/en/stable/index.html) support.
You can also create a docker to integrate the tool and language of your choice!
See the [codacy-engine-scala-seed](https://github.com/codacy/codacy-engine-scala-seed) repository for more information.

## What happens if I have multiple configuration files in my repository?
The configuration file at the root of the repository defines the main configuration for the project. Configuration files located in subdirectories can override or extend this main configuration, but they cannot relax or revert any restrictions defined at the root level.

For example, if a pattern is ignored in the root configuration, it remains ignored in all subdirectories. Subdirectory configurations can ignore additional patterns, but cannot re-enable those that were disabled at the root.

This ensures consistent baseline behavior across the project, while still allowing directory-specific customization when needed.

## How to run SQLFluff for the dialect of my codebase
By default, we run SQLFluff with the dialect Postgres because the flag --dialect is mandatory. If your codebase is based on another dialect above, please create a simple **.sqlfluff** config file in the root of your repository with the following content (let's use Oracle as an example):

```text
[sqlfluff]
dialect = oracle
```
It will run for all existing rules for the dialect Oracle

If you want to ignore some of the rules, please use the same configuration file:

```text
[sqlfluff]
dialect = oracle
exclude_rules = LT01,RF01
```

It will run for all existing rules, excluding LT01 and RF01, for the dialect Oracle


## Usage

You can create the docker by doing:

  ```bash
  docker build --no-cache -t codacy-sqlfluff:latest .
  ```

The docker is ran with the following command:

  ```bash
  docker run -it -v $srcDir:/src codacy-sqlfluff:latest
  ```

## Generate Docs

1. Update the version in `requirements.txt`

2. Run the DocGenerator to update all the patterns/descriptions and the patterns.xml (from all-patterns test)

    ```bash
    python<version> src/doc_generator.py
    ```

## Agent Playbook: Updating This Repository End-to-End

This section is written for an AI coding agent (or a human) tasked with updating this repo — most commonly bumping the wrapped SQLFluff version, but also base image / dependency / orb bumps. Follow it top to bottom; it tells you what to change, how to regenerate derived files, how to test locally, and how to interpret CI so you can iterate on failures without guessing.

### 1. What this repository is

This is a **Codacy engine**: a small Python wrapper (`src/codacy_sqlfluff.py`) that packages [SQLFluff](https://docs.sqlfluff.com/en/stable/index.html), an open-source SQL linter, as a Docker image Codacy's platform can run against a customer's SQL code. There is no Scala/sbt anywhere in this repo — it is pure Python, and there is no build step beyond `pip install` and a Docker build.

The `docs/` directory is machine-consumed configuration, the same way it is in other Codacy tool engines:

- `docs/patterns.json` — the full list of SQLFluff rules ("patterns") Codacy knows about, their severity/category, and which are enabled by default. **Generated file, do not hand-edit.**
- `docs/description/description.json` + `docs/description/*.md` (75 files as of this writing, one per rule) — human-readable titles/descriptions per pattern, used in the Codacy UI. **Generated file, do not hand-edit.**
- `docs/multiple-tests/all-patterns/patterns.xml` — list of all pattern IDs, also regenerated by the generator. `docs/multiple-tests/*/results.xml` and `*/src/*` are hand-maintained fixtures used by `codacy-plugins-test`'s `multiple` test.
- `docs/tool-description.md` — short blurb about the tool, hand-maintained.

All the generated artifacts above come from **`src/doc-generator.py`** (note: the filename uses a hyphen, `doc-generator.py`, not the underscore `doc_generator.py` shown in the older "Generate Docs" section above — that section is stale/inaccurate, verify against `src/` before trusting it). The generator:
1. Downloads every rule file from `https://api.github.com/repos/sqlfluff/sqlfluff/git/trees/main?recursive=1` (i.e. SQLFluff's `main` branch on GitHub, **not** a version tag — it needs network access).
2. Parses each rule's Python AST to extract the rule ID, name, and docstring.
3. Reads the pinned version out of `requirements.txt` (`get_sqlfluff_version()`) and writes it into `docs/patterns.json`.
4. Regenerates `docs/description/*.md`, `docs/description/description.json`, `docs/patterns.json`, and `docs/multiple-tests/all-patterns/patterns.xml`, pruning stale description files for rules that no longer exist upstream.

There is no sbt/DocGenerator-Scala pattern here — it's a standalone Python script with no CLI framework, just `python src/doc-generator.py` run from the repo root.

### 2. Files that encode versions — check all of these on every update

| File | What it controls | What to check |
|---|---|---|
| `requirements.txt` → `sqlfluff==<version>` | Which SQLFluff release is installed and linted-against; also the value the doc generator writes into `docs/patterns.json` | Bump to the target version. This is the primary "version" for this repo. |
| `requirements.txt` → `jsonpickle==<version>` | Serialization library used by `src/codacy_sqlfluff.py` | Only bump if asked or if `sqlfluff`'s bump forces a transitive requirement; not tied to SQLFluff bumps historically. |
| `Dockerfile` → `FROM python:<version>-alpine<version>` | Python/Alpine base image the engine runs on | Bump only when it's stale/insecure or when SQLFluff's new version requires a newer Python (check SQLFluff's release notes / `pyproject.toml` `python_requires`), not opportunistically — see commit `12f4016` where the Alpine patch version was bumped alongside a SQLFluff bump, and `README.md`'s "Python compatibility" line was updated in lockstep with the base image (commit `58d40db`). |
| `docs/patterns.json` → `"version"` | Displayed/tracked SQLFluff version; the field the doc generator itself writes | Do not hand-edit — regenerate via `src/doc-generator.py` after bumping `requirements.txt`. |
| `README.md` → "Python compatibility" section | Documented supported Python version | Update to match the new `Dockerfile` base image's Python version when that changes. |
| `.circleci/config.yml` → `codacy/base` orb, `codacy/plugins-test` orb | Shared CircleCI steps (checkout/versioning, docker build/publish, tagging) and the `codacy-plugins-test` runner | Check current published orb versions if asked to bump them; not tied to SQLFluff version bumps historically (no such bump found in git history for this repo). |

Look at recent bump commits for the real shape of a typical diff: `git log --oneline --all | grep -i bump`, then `git show <hash>`. Concrete precedents in this repo's history:
- `f6d597d` / `7fb5bd6` ("Bump sqlfluff 3.4.1"): only `requirements.txt` + `docs/patterns.json` changed — a pure patch-version bump with no rule-set changes.
- `12f4016` ("Bump SQLFluff 3.4.2"): `requirements.txt`, `docs/patterns.json`, and `Dockerfile` (Alpine patch bump) changed together.
- `aa92aad` ("Bump SQLFluff 3.5.0"): a minor-version bump.
- `be3ce14` ("Bump SQLFluff 4.0.4 and improve timeout handler"): version bump plus unrelated behavior fix in `src/codacy_sqlfluff.py`.
- `58d40db` ("Add flag large_file_skip_byte_limit and Bump version 4.1.0"): `requirements.txt`, regenerated `docs/description/*.md` + `docs/description/description.json` + `docs/patterns.json` + `docs/multiple-tests/all-patterns/patterns.xml` (new/changed rules picked up by the generator), `README.md` Python-compatibility line, and a `src/codacy_sqlfluff.py` feature change — i.e. a version bump that also picked up new upstream rules needs the generator run and its output committed, not just `requirements.txt`.

### 3. Step-by-step update procedure

1. **Bump the version** in `requirements.txt` (`sqlfluff==<new-version>`), scoped as the task requires.
2. **Regenerate the docs.** Requires Python 3 with `requests` installed, plus network access to `api.github.com`/`raw.githubusercontent.com`:
   ```bash
   pip install -r requirements.txt requests
   python src/doc-generator.py
   ```
   This rewrites `docs/patterns.json`, `docs/description/description.json`, `docs/description/*.md`, and `docs/multiple-tests/all-patterns/patterns.xml`. Review the diff for new/removed/renamed rules — new rules default to `"enabled": false` unless their 4-char rule ID prefix is in the generator's `enabled_rules` list, so double-check whether any newly-added rule should be added to that list in `src/doc-generator.py` before committing.
3. **Bump the Python/Alpine base image in `Dockerfile`** only if required by the new SQLFluff version's Python support, and update the "Python compatibility" line in `README.md` to match.
4. **Build the Docker image** (same as CI):
   ```bash
   docker build --no-cache -t codacy-sqlfluff:latest .
   ```
5. **Smoke-test locally:**
   ```bash
   docker run -it -v $srcDir:/src codacy-sqlfluff:latest
   ```
6. **Run `codacy-plugins-test` locally** before pushing — clone https://github.com/codacy/codacy-plugins-test and run its DockerTest against your local image tag. CI only runs the `multiple` test (`run_multiple_tests: true`, `run_json_tests: false`, `run_pattern_tests: false` in `.circleci/config.yml`), so at minimum validate the `docs/multiple-tests/*` fixtures still match actual output; running `pattern`/`json` too is a useful extra sanity check even though CI doesn't require it.
7. **Iterate on failures**, re-running only the relevant DockerTest command after each fix, and re-running `src/doc-generator.py` if a fixture mismatch turns out to be a stale generated file rather than a real regression.
8. **Commit** the version bump together with the regenerated `docs/` files (and any `Dockerfile`/`README.md` changes) in one change.
9. **Push and open a PR.** CI (`.circleci/config.yml`) runs `codacy/checkout_and_version` -> `publish_docker_local` (builds and saves the image) -> `plugins_test` (`codacy_plugins_test/run`, multiple-tests only) -> `codacy/publish_docker` (master only) -> `codacy/tag_version`.
10. **Poll the PR's real CI checks until they all pass — local validation is NOT the finish line.** After every push, run `gh pr checks <pr-url>` and keep re-polling (short sleep while any check is `pending`) until all checks finish. If a check fails, fetch its actual log (CircleCI API/UI for the failing job — don't guess), find the true root cause, fix it, push again (never `--no-verify`, never force-push), and re-poll. Repeat until every check is green. The CI environment's toolchain can differ from your local one (different `pip`/Alpine cache state, different network access to the SQLFluff GitHub API, etc.), so a clean local run does not guarantee CI passes. Only stop iterating when every check passes, or you hit a genuine product/infra decision that needs a human — in which case explain it in the PR rather than guessing.

### 4. Common failure modes and fixes

| Symptom | Likely cause | Fix |
|---|---|---|
| `multiple` DockerTest fails on `all-patterns` or `with-config-file` fixtures | Rule added/removed/renamed upstream between SQLFluff versions, or a rule's default enablement/severity changed | Re-run `src/doc-generator.py` and compare `docs/patterns.json`/`docs/description/*` diffs against the fixture's expected `results.xml`; update the fixture only after confirming the new behavior is correct, not just to make the test pass. |
| `src/doc-generator.py` produces a mostly-empty or truncated `docs/description/*` set | GitHub API rate limiting or network failure mid-download (script has no retry/backoff) | Re-run once network/rate-limit conditions clear; consider adding a `GITHUB_TOKEN` to the `requests.get` calls if this becomes a recurring issue. |
| New/changed rule is unexpectedly `"enabled": false` (or vice versa) in `docs/patterns.json` after regenerating | The generator's hardcoded `enabled_rules` list in `src/doc-generator.py` doesn't include the rule's 4-character ID prefix | Decide whether the rule should ship enabled by default and edit `enabled_rules` in `src/doc-generator.py` accordingly, then re-run the generator. |
| Docker build fails installing `requirements.txt` | New SQLFluff version needs a newer Python than the pinned Alpine base image ships | Bump the `python:<version>-alpine<version>` tag in `Dockerfile`, and update the "Python compatibility" line in `README.md` to match. |

### 5. Definition of done

- `requirements.txt` (and `Dockerfile`/`README.md` if the Python base image changed) reflects the target version(s).
- `docs/patterns.json`, `docs/description/description.json`, `docs/description/*.md`, and `docs/multiple-tests/all-patterns/patterns.xml` regenerated via `src/doc-generator.py` and committed, with any `enabled_rules` decisions made deliberately.
- Docker image builds successfully (`docker build --no-cache -t codacy-sqlfluff:latest .`).
- `codacy-plugins-test`'s `multiple` tests (at minimum — matching what CI runs) pass locally against the freshly built image.
- **After pushing and opening/updating the PR, every CI check on it is green.** Poll `gh pr checks <pr-url>` and iterate on any failure (fetch the real CI log, fix, push, re-poll) until all pass — a passing local build is not sufficient, because the CI toolchain can differ from your local one (see step 10 above).
